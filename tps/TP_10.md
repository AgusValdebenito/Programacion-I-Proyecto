# 📝 Trabajo Práctico N°10: Despliegue de la Aplicación en la Nube

## 🎯 Objetivo

Desplegar la aplicación completa en la nube: la **API** (Django \+ DRF \+ PostgreSQL), el **frontend** (React \+ Vite) y **almacenamiento de medios** (imágenes), de modo que queden accesibles desde internet con URLs públicas. Se debe documentar el proceso de publicación y adjuntar capturas de la API, el frontend y el almacenamiento funcionando en producción.

---

## 📦 Entregables

1. **URL pública de la API** (ej.: `https://mi-api-production.up.railway.app`).  
2. **URL pública del frontend** (ej.: `https://mi-app.vercel.app`).  
3. **URL de Cloudinary** (ej.: `https://res.cloudinary.com/tu-cloud/image/upload/...`) si el proyecto usa subida de imágenes.  
4. Repositorio con la configuración de despliegue (Procfile, `railway.json`, `vercel.json`, Dockerfile opcional).  
5. Capturas de:  
   - Swagger/Redoc (drf-spectacular) abierto en producción.  
   - Respuesta exitosa de `/api/health/` (o similar).  
   - Endpoint protegido accedido con credenciales reales (200/401 según corresponda).  
   - El frontend cargando datos desde la API en producción.  
   - Subida de imagen funcionando (si aplica) y visible en Cloudinary.  
   - El panel del proveedor mostrando el servicio "Running".  
6. Documento paso a paso "Cómo se subió" (ver plantilla al final).

---

## 🧰 Requisitos previos

- Proyecto completo funcionando localmente (backend TP1–TP4 y frontend TP5–TP9).  
- Cuentas creadas en los servicios de despliegue (Railway, Vercel, Cloudinary).  
- Base de datos: **PostgreSQL** (en Railway/Render/Fly o externo).  
- Archivo `.env` local con las variables (no subirlo al repositorio).  
- `requirements.txt` actualizado con `gunicorn`, `whitenoise`, `django-storages` (si usás Cloudinary).

## ☁️ Parte A: Desplegar la API

### Opción 1: Deploy desde Git (recomendado para la cursada)

**Railway / Render / Fly.io** detectan automáticamente el tipo de proyecto y construyen desde el repositorio. **No necesitás Docker** si usás esta vía.

#### Con Railway (método principal)

1. Crear proyecto en Railway → "Deploy from GitHub repo".  
2. Seleccionar tu repo y la **rama** (ej.: `main`) o un **tag** (ej.: `v1.0.0-deploy`).  
   - *Tip*: usar un tag permite desplegar versiones específicas sin tocar `main`.  
3. Railway detecta `Procfile` o `railway.json` y construye.  
4. Agregar servicio **PostgreSQL** y vincularlo.  
5. En "Variables", pegar el contenido de tu `.env` (sin el archivo):  
     
   DATABASE\_URL=postgresql://...  (Railway la inyecta automáticamente)  
     
   SECRET\_KEY=tu-secret-key  
     
   DEBUG=False  
     
   ALLOWED\_HOSTS=.up.railway.app  
     
   CLOUDINARY\_URL=cloudinary://...  (si usás Cloudinary)  
     
6. Build command: `pip install -r requirements.txt && python manage.py collectstatic --noinput`  
7. Start command: `gunicorn config.wsgi`  
8. En "Settings" → "Deploy": activar "Auto-deploy" si querés que cada push a `main` redeployee.  
9. Verificar `/api/docs/` y `/api/health/`.

#### Con Render (alternativa)

1. New → Web Service → conectar repo GitHub.  
2. Build Command: `pip install -r requirements.txt && python manage.py collectstatic --noinput`  
3. Start Command: `gunicorn config.wsgi`  
4. Agregar PostgreSQL (Render lo provee).  
5. Variables de entorno igual que arriba.  
6. Render usa `render.yaml` opcional para guardar la config como código.

#### Con Fly.io (requiere Dockerfile)

1. `fly launch` detecta Django y genera `Dockerfile` \+ `fly.toml`.  
2. `fly postgres create` para la BD.  
3. `fly secrets set` para las variables.  
4. `fly deploy` — compila la imagen Docker y sube.

>   
> **¿Git o Docker?** Para la cursada: **Git (Railway/Render)**. Docker (Fly.io) es opcional para quien ya lo domine. El TP se aprueba con cualquiera, pero el camino estándar es Git \+ Railway.

## 🌐 Parte B: Desplegar el Frontend

### Vercel (recomendado)

1. Importar el mismo repo GitHub en Vercel.  
2. **Root Directory**: `frontend/`  
3. **Build Command**: `npm run build` (Vercel lo detecta solo)  
4. **Output Directory**: `dist` (Vite usa `dist/`, no `build/`)  
5. Variables de entorno:  
     
   VITE\_API\_URL=https\://mi-api-production.up.railway.app/api  
     
6. Deploy → Vercel genera URL `https://tu-app.vercel.app`.

>   
> **Deploy desde tag**: En Vercel, Settings → Git → "Production Branch" \= `main` (o el tag que uses). Cada push a esa rama/branch redeployea.

### Netlify (alternativa)

1. New site from Git → conectar repo.  
2. Base directory: `frontend/`  
3. Build command: `npm run build`  
4. Publish directory: `dist`  
5. Variables de entorno igual que Vercel.

## 🖼️ Parte C: Cloudinary (solo si el proyecto sube imágenes)

Si tu modelo tiene `ImageField` o `FileField` (ej. fotos de productos), **no guardes archivos en el disco del servidor** (en Railway/Render el filesystem es efímero). Usá Cloudinary.

**Qué hacer:**

1. Crear cuenta en Cloudinary ([https\://cloudinary.com](https://cloudinary.com), tier gratis 25 GB/mes).  
2. Obtener `CLOUDINARY_URL` del Dashboard.  
3. Instalar dependencias: `pip install django-storages cloudinary-storage`.  
4. Configurar `settings.py` para usar Cloudinary como `DEFAULT_FILE_STORAGE`.  
5. Definir `CLOUDINARY_URL` en las variables de entorno del proveedor (Railway/Vercel).  
6. Verificar en el panel de Cloudinary (Media Library) que las subidas via API aparecen correctamente.

>   
> No se evalúa el código de configuración, se evalúa que **la subida de imágenes funcione en producción** y se vea en Cloudinary.

## ✅ Criterios de aprobación

- La API responde públicamente (`200 OK`) a endpoints abiertos.  
- Los endpoints protegidos devuelven `401` sin credenciales y `200` con token válido.  
- Swagger/Redoc es accesible en producción.  
- El frontend público carga datos reales desde la API en producción.  
- **Si hay subida de imágenes**: funcionan y se ven en Cloudinary.  
- El código de despliegue es reproducible (quien corrige puede repetirlo).  
- Las capturas están incluidas y bien identificadas.
